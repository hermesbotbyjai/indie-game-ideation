Auto-Research Loops

A solo developer, Codex, and a tight loop on a B200 kernel contest. 12th place out of 183, 232x faster than the baseline, 1,500 submissions over 14 days. The result is interesting. The method is the lesson.

The model in one sentence

One sentence, then we build on it.

Auto-research is what happens when an LLM agent is wrapped in a tight optimization loop with a measurable oracle — a benchmark, a leaderboard, a verifier — and the harness (the objective, the eval, the standing instructions, the submission discipline) is the product, while the model just fills in iterations inside it.

If you can write that sentence down, you've got the concept. Everything below is how to actually run one.

The mental model

The loop, drawn once.

Look at this picture every time you read a new auto-research story. Every loop looks like this. The variation is in what each block actually contains.

Read it clockwise. The agent submits something, the oracle judges it, the log records the result, a new idea is chosen, the harness steers it, the agent executes. One round = one submission. 1,500 submissions = 1,500 rounds = the entire contest.

The walkthrough

Five ideas, in order.

Step 01

The oracle makes the loop possible

GPU kernels are the canonical auto-research target because two things are simultaneously true: the kernel either produces the right matrix or it doesn't, and the wall-clock time is a single number. Both halves of the feedback signal are machine-verifiable. No human review, no ambiguous taste call, no plausible-but-wrong output sitting in the log for weeks before someone notices.

This is what separates a hill-climbable problem from a research-taste problem. If your oracle requires a human to grade it, you don't have a loop, you have a feedback queue.

Why this matters Before you build a loop, ask: can I write a script that returns a number in under five minutes for arbitrary input? If not, your loop is going to stall waiting for humans.
Step 02

The harness is the product

Look at what Sankalp actually wrote. It's not clever prompting. It's three files: problem_statement.md (what to optimize), AGENTS.md (standing rules for the agent), log.md (bookkeeping of every submission, every shape, every result). Karpathy's autoresearch repo is the same shape: a single program.md the human edits, a train.py the agent edits, a fixed prepare.py nobody touches.

The human's prompt is the spec. The agent's prompt is a code file the human curated over weeks. The log is the agent's working memory across sessions.

Why this matters Three files, three roles, one rule. The thing that's fixed (prepare.py / oracle) is the ground truth. The thing that moves (train.py / submission) is the search space. The thing the human owns (program.md / AGENTS.md) is the policy. Most failed auto-research attempts collapse because the policy is implicit, not written down.
Step 03

Beam of candidates, not single-incumbent hill climb

The naive loop holds one incumbent and rejects everything that scores worse. That's the fastest way to get trapped. Sankalp calls this out as the bottleneck between 3,000 µs and 1,800 µs: "I kept a single best candidate against which new candidates were tested. If the agent tries a new structural idea, it's highly likely to score less than the current best. After a few iterations it may outperform — but we killed it on the first try."

The fix is a small beam (usually three to five) of live candidates. Each beam entry records parent, hypothesis, what changed, current best, and next combination. One beam exploits the current best. One beam is the near-miss. One beam is a high-risk structural attempt. Promotion is based on hypothesis validity plus enough data, not on immediate score.

Why this matters Single-incumbent hill climbing optimizes the immediate objective at the cost of exploration. The beam pattern is how AlphaGo-style algorithms survive low-confidence moves: keep the option alive long enough to learn whether it pays. Same idea, different scale.
Step 04

Where the loop breaks

Three failure modes show up in every long auto-research run. Knowing them in advance is half the defense.

Oracle gaming. The agent finds a hole in the metric and exploits it. Sankalp calls out benchmark artifacts as the tell — any agent optimizing against a metric will find the metric's holes first. The fix is a verifier that itself runs end-to-end, not just the surface metric.

Local maxima. The agent settles on a configuration that is "best" given its current framing, even though a structural change would unlock 10x more. The fix is the beam from step 3, plus periodic fresh-context resets and explicit "go read a paper" instructions.

Drift collapse. Over many sessions the agent's idea space shrinks because every idea has to beat the current best. The fix is hard. Maintain a small but persistent "wild card" slot. Encourage the model to take risks and try ambitious changes. Use a stronger advisor model that produces more varied ideas. Occasionally clean up code and clear context so the agent doesn't keep mutating a frozen mental model.

Why this matters Auto-research runs that look magical in screenshots have all survived at least one of these three. The ones that didn't end up optimizing the wrong thing, very best middle, very confidently.
Step 05

The human's job collapses to three things

Sankalp is honest about what he actually did for those 14 days. Not clever prompts. Three things.

Pick the objective. Build the eval loop. Know enough to recognize a real gain from a benchmarking artifact. That's it. The agent did the iteration. The human steered every two to three hours when the agent got stuck, asked it questions via /btw without pausing the loop, and trusted it overnight on days when the direction was set.

Reading the output is the part that looks like taste. Knowing that the agent just discovered a real 50 µs improvement versus a benchmarking artifact versus a numerical trick that won't survive larger shapes — this is what makes you the architect rather than the operator.

Why this matters Three jobs, not twenty. The architect's job in an auto-research system is to be the verifier of the verifier, not to be the agent. If you can't read the output well enough to spot a benchmarking artifact, the loop will run forever and you won't know.
Common confusions

Four things people get wrong about this.

×Isn't this just RL with extra steps?
No. RL updates model weights using gradient signal from a reward. Auto-research updates source code using edit-rule signal from a score. The "policy" being optimized is text in a file, not weights in a tensor. Different optimization surface, different bottlenecks.
×The model must be the smartest one.
It helps but it isn't the load-bearing variable. Sankalp's GPT-5.5 Codex outperformed a "principal engineer at NVIDIA" not because it was smarter on a per-call basis, but because it could iterate 1,500 times in 14 days. The volume of cheap attempts matters more than the depth of any single one.
×Auto-research replaces the researcher.
It replaces the iteration. The human still owns the objective, the eval loop, and the artifact-vs-real-gain read. This is why "domain expertise accelerates harness design and human-in-the-loop steering" — you need to know enough about the problem to write program.md that points at the right thing.
×Submit fast, submit always.
Auto-research explicitly says no. AGENTS.md for the kernel run included "Space leaderboard submissions out. Do not stack rapid back-to-back submissions." "Treat a timeout as inconclusive, not as a correctness/performance rejection." Without that discipline the loop generates noise faster than it generates signal.
