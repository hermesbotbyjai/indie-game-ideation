DAY 7: AI INFRASTRUCTURE / ROUTING

LLM Model Routing

A per-action router that picks the cheapest model on the Pareto frontier for every API call, tracks session state with a hidden Markov model, and skips a switch when filling a fresh prefix cache would cost more than it saves.

Why one big model is leaving 50%+ of cost on the table for coding agents.
How an HMM + classifier narrows a 10^100 decision space to something RL can solve.
The cache-eviction math that decides when a model switch is even worth it.
Why “route per action” beats “route per turn” in production code agents.
THE MODEL IN ONE SENTENCE
Mental model A model router is a learned selector that scores every upcoming action against a Pareto frontier of available models and picks the cheapest one whose expected quality is high enough, while a hidden Markov model on the session and a prefix-cache accounting layer keep the choice stable across turns.
THE MENTAL MODEL

One image: a router in the middle of a 50-call coding session.

Imagine Claude Code making 50 LLM calls to fix a flaky test. The router sits between your agent and every provider, scoring each call against the frontier, the session HMM, and the live cache state. Watch the decision flow per action: the same session, four different model picks, none of them the most expensive one on the list.

Read this left to right. Every request from the agent flows through the router. The router looks at the session HMM, picks a model bucket, runs the cache-eviction calculation, and forwards to one model on the roster. The chosen model processes the request and the response plus its new cache state flow back so the next call can score again.

WALKTHROUGH

Six pieces, one architecture.

The router is not a single model. It is a pipeline. Each piece solves a problem that bites you the moment you turn the system on in production.

1. The Pareto frontier

Before you can route, you need to know what you are routing over. The interesting axis is not "best model" (you already have that). It is the curve of cost vs. quality across every model in your roster. Plot them, mark the ones no other model dominates on both axes, and you get a small set of candidates. The router only chooses from those.

FIGURE 1 · COST VS. QUALITY PLOT, PARETO FRONTIER MARKED

Why this matters A roster of 10 models collapses to 4 to 6 candidates on the frontier. Every dominated model is wasted search space. The router only needs to score among frontier models, which means the action space the learned scorer has to reason over drops by half before training even starts.

2. The decision space, and why naive RL fails

Imagine a 50-turn coding session. The agent makes 50 API calls. If you have 10 candidate models, there are 10^50 possible sequences of model choices through the session. That number is not a typo. You cannot explore that space with reinforcement learning, no matter how much compute you throw at it. The first generation of routers tried, and they did not work.

FIGURE 2 · DECISION TREE OF MODEL CHOICES ACROSS TURNS

Why this matters You have to shrink the search space before you let the learner touch it. The two levers that actually work are (a) Pareto filtering (already cut the roster) and (b) grouping models into buckets the classifier can pick from, instead of asking the scorer to pick from 10 individuals. That is what the next step does.

3. The HMM + classifier: state before choice

Two coding-agent sessions that look identical to a turn-level classifier can be in completely different states. One is three turns into a careful refactor, the other is twenty turns into a debug spiral. A naive classifier routes them the same way and gets both wrong. A hidden Markov model on the session tracks where you are and how you got there, then a small classifier maps that hidden state onto a bucket of similar models. The search space collapses from 10^50 paths to a few thousand per session.

FIGURE 3 · HMM HIDDEN STATES PICK A BUCKET, RL SCORES INSIDE IT

Why this matters The HMM is doing the same job that the prefix cache would do if it were big enough. It carries the "where am I in this session" information that a stateless scorer would lose, and it does so in O(1) per turn. Without it, you are routing blind.

4. Per-action, not per-turn

Most early routers picked a model for the whole session. That is wrong for coding agents. A typical turn has two or three distinct sub-actions: read a file, plan an edit, write the edit, run a test, summarize. Those sub-actions have wildly different quality bars. The router picks per action, not per turn, which is why the latency budget is 50 ms and the scorer is small. A full LLM call to decide the model would defeat the point.

FIGURE 4 · INSIDE A SINGLE TURN, EACH ACTION IS ROUTED INDEPENDENTLY

Why this matters "Plan the fix" needs a strong model because the agent is choosing what to do. "Read the file" is mechanical and any model handles it. "Summarize for the user" is low-stakes and a cheap model is fine. Per-action routing pays for the expensive model only on the one action that needs it. On Terminal-Bench, this distinction is where most of the cost savings come from.

5. The cache-eviction accountant

Here is the part that decides whether the router actually saves money or just shuffles spend around. Every model has a prefix cache, and if you switch models, you pay the full cost to fill the new cache. The accountant models the expected value of staying vs. switching: how much you save on this and future calls by using the better model, minus the one-time cache-fill cost. If the switch does not pay back in N turns, the router stays put. Most cost wins in production routers come from this subsystem, not from "pick the cheapest model."

FIGURE 5 · SWITCH PAYS $0.37 UPFRONT; ONLY WORTH IT IF QUALITY LIFTS FUTURE CALLS ENOUGH

Why this matters Without this, the router picks the frontier model every time quality is unclear, and the cache savings go to zero. With it, the router learns to stay on a strong mid-tier model through long stretches of "easy" turns and only switch when a hard sub-action justifies the cache fill.

6. Training data: how the scorer learns what “good enough” is

The router is two small learned models (the HMM and the classifier), trained on labeled coding-agent sessions. The labeling step is the unsexy part that takes most of the engineering time. A frontier LLM scores every action in thousands of recorded sessions for quality and cost, and the bootstrap runs in a loop: the labeled data trains the router, the router's decisions are compared against the labels, the disagreements get re-labeled by a stronger judge, and the loop continues. This is where "labels" come from in a system that has no human-graded ground truth.

FIGURE 6 · THE TWO-LEARNER LOOP THAT MAKES THE ROUTER WORK

Why this matters The router does not learn from "did the user upvote this code." It learns from the gap between the cheap model's action and the frontier model's action, and the cost of the difference. That is why the labeled data is the moat, not the architecture. Anyone can copy the architecture.
COMMON CONFUSIONS

Four things people get wrong.

Each of these burned real engineering time. Read them before you build one.

CONFUSION 1

"A router is just load balancing. Pick round-robin and you are done."

No. Load balancing assumes the requests are interchangeable. LLM calls are not: a planning call and a file-read call have different quality bars, and a wrong pick on a planning call is a wrong code change. The whole point of a learned router is that it conditions on the call's role in the session, which is information round-robin throws away.

CONFUSION 2

"Just pick the cheapest model that works."

This is the right intuition at the action level and the wrong abstraction at the session level. The cheapest model that works today may be the wrong one because the cache is on a different model, or because the session is about to enter a hard sub-action. The router has to look ahead, not just at the current call.

CONFUSION 3

"Route per turn, not per message, because turns are the natural unit."

A turn is a UI boundary, not a workload boundary. One turn of a coding agent contains reading, planning, writing, and summarizing, and those want different models. The Weave Router team reports that this single change (per-action vs per-turn) is one of their biggest cost wins. If your router only picks once per turn, you are leaving 30 to 40% of the savings on the table.

CONFUSION 4

"Use the strongest model to route. Quality of choice matters more than latency."

A 500 ms decision on every API call is a 500 ms tax on every action, and a model call to pick a model often costs as much as a cheap model call would have. Production routers cap the decision at around 50 ms and use a small learned scorer. The router itself is not the product. The whole architecture is the product.
