Source control
for agents

When coding is the cheap part, git stops being the right graph. What Anthropic's Scion teaches us about designing a repo that 30,000 merges per day don't break.

Why a 100 GB main history is no longer an edge case: agent-native teams ship at orders of magnitude past what git was designed for.
The five principles Scion commits to that git doesn't: online clients, asymmetric roles, full programmatic surface, lock-free commits, sparse-by-default checkouts.
What a "changeset" really is when the unit of work becomes a write-ahead-log entry instead of a snapshot.
What staff engineers should steal for other agent-scale systems, not just SCM.
The model in one sentence

Source control stops being a graph of files to clone and becomes a queryable, always-online service that scales with the size of the change, not the size of the repo, because at agent scale the client is never offline and almost never needs a full working copy.

Conceptual shift: git hands every client the whole graph; Scion answers only the questions clients ask, with tiered caches and no materialized copy anywhere on the server side either.

Walkthrough

Five principles,
one walking contradiction.

The whole Scion design is an unfolding of a single observation. Each principle is what you do once you actually accept the prior one.

1. Clients are always online, and that changes everything.

Git's deepest assumption is that you might be on a plane. That's why you carry the whole repo, why git log works offline, why blame is a local operation. Scion just deletes the assumption.

The Anthropic team noticed that they were running git as if it were centralized, but every real client was an agent or a CI job that is online by definition. The properties that make git good for distributed developers were the ones actively breaking them at scale.

why this matters If your clients are online, the local object cache can be small and the server can be the source of truth. Don't run a distributed algorithm when no one is distributed.

2. The server does the work; the client keeps the bytes.

In git, every clone is also a server. A clone can host a remote that other clones fetch from. Anthropic ripped that out. In Scion, the server is authoritative and the client is deliberately dumb. The server creates commits, performs merges, rebases, and answers blame queries.

This lets the client discard almost everything. It doesn't compute diffs over local history because there isn't any local history worth mentioning. The trade is that one part of your system now needs to be very good at a lot of things at once, but you also get to scale the two halves independently.

why this matters Symmetry in distributed systems feels like robustness. It also tends to be the thing that breaks first at scale. Decide which role is the load-bearing one and stop pretending every node plays both parts.

3. A commit becomes a write-ahead-log entry.

A git commit points to a tree. Cheap to write if you're computing the tree locally, expensive if you have to materialize it across a server. Scion flips it: a changeset is just the list of files that changed relative to the first parent, plus content-addressed pointers to the new blobs.

No packfiles, no refs to move, no cross-server coordination. The Spanner row that holds the ref is a compare-and-swap that happens after the changeset already exists. The cost of a commit now scales with the size of the change, not the size of the repo. That's the whole throughput trick.

why this matters When merge rate is 30,000 a day, the question "how big is a commit" needs to mean bytes-touched, not repo-touched. Any system whose cost is the wrong one of those will melt under agent load.

4. The checkout is optional.

The previous version of this story at Anthropic was, "yes, you have to have a working copy to do anything." Scion quietly makes that false. A CI job that needs to know if a PR touches build config doesn't need to materialize anything. It calls an API and gets back a list of paths.

This is more than a perf win. It means the system's prime surface is the API. Every question a client used to ask by reading its local repo becomes a function call. Anthropic's automated bisect, revert, and merge-queue "superfans" all lean on this.

why this matters When the API is the product and the working copy is a thin materialization, agents and humans stop being different kinds of users. Agents just call more of the API more often.

5. Sparse by default, tiered caching, no materialized copy.

Git's fetch protocol asks the server, "what do I have, what am I missing, give me a packfile." Scion's protocol asks, "give me exactly this tree, exactly these blobs." It's a tree walk, not a packfile exchange. Every object is content-addressed and immutable, so any cache can answer any request without coordinating with the others.

The result is a three-tier topology with a 99% cache hit rate at every layer: scion-daemon on each node, scion-cache per region streaming from memory, scion-servers reading from Spanner. The footprint is 200x smaller than their previous git-mirror setup, and CI jobs check out code in seconds.

why this matters When the cost of fetching scales with what you actually need rather than what you might need, the whole "should I cache this?" question disappears. Most distributed systems are paying for bytes that nobody reads. Stop.

Common confusions

Five things
readers get wrong.

This section is the one that makes the rest worth saving. If you only remember two of these, remember "git at scale" and "you're not Anthropic".

01 / the size

Scion matters because Anthropic needed to handle a huge repo.

It matters because agent-coded projects push repo size past the design point of every distributed VCS we already had. Piper and Sapling solved the human-scale monorepo; Scion is for the agent-scale one where merge volume dominates. Jai's game studio will hit Sapling-scale problems before it hits Scion-scale problems, but the trajectory is the same.

02 / the lesson

You should replace git with a service.

You should ask which of your system's invariants depend on the client being offline and which ones only need the client being reachable. Most "git-like" assumptions are hiding in places that aren't source control: search indices, build caches, asset registries. Identify those, then design the online version of each.

03 / the cost model

A changeset is just a commit with fewer fields.

The interesting move is that commit cost now scales with change size, not repo size. That is the load-bearing claim. Any system whose per-write cost was previously the wrong one of those two scales badly under agent load. Hunt for those; the SCM is the canary, not the only thing on fire.

04 / the workflow

Anthropic's engineers spent their time reading code.

They mostly read the intent of a change and spent a lot of time telling Claude "no." The interesting failure mode wasn't bugs; it was agents brute-forcing questions that should have been API calls (e.g. reading the commit log linearly to find when something merged) because the system's invariants weren't documented well enough for the model to see them.

05 / the takeaway

Use Scion if your repo is big.

Scion is open-sourcing neither the server nor the format; Anthropic's post is a design study, not a distribution. The takeaway is the five principles, plus the superfan pattern, plus the realization that CI at agent throughput is no longer a global lock problem. Use whatever SCM you have, but rebuild the next layer up the stack in this style.
