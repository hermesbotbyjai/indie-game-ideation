Conditional Memory via Scalable Lookup:
How DeepSeek's Engram Adds an N-gram Table to a Transformer

Transformers have a sparse computation axis (Mixture-of-Experts) but no sparse memory axis. DeepSeek's Engram module fixes that by hashing recent token spans into a giant embedding table and adding the result as a gated residual. Early layers stop rebuilding static knowledge, and the rest of the network gets its depth back for reasoning.

  • What "conditional memory" means as a sparsity axis, and why it is different from MoE
  • How multi-head hashed N-gram lookup works in O(1) and why collisions are not fatal
  • Why the gate matters more than the table (context-aware fusion, not dumb lookup)
  • The U-shaped allocation curve: ~20-25% of inactive weights go to Engram, the rest to experts
THE MODEL IN ONE SENTENCE

Engram is a hash-addressed N-gram embedding table that the transformer queries in O(1) per token and adds to the residual stream through a learned gate, so the network offloads static local patterns to a lookup and spends its depth on the parts of language that actually need computation.

THE MENTAL MODEL

Tokens go through the backbone, but the table looks them up

The full pipeline reads left to right. The top lane is the normal transformer block. The bottom lane is Engram: it pulls the suffix N-grams of every position, hashes them into a learned embedding table, projects the lookup through a gate, and adds the result to the residual stream right where the attention block would have started.

Why this matters. Every existing dense model pays attention and FFN compute to "remember" that Paris is a city, that New York usually means New York, that import numpy as np is a Python incantation. Engram does that with a hash and a vector add. The compute you save is the depth the rest of the network spends on actual reasoning, which is why BBH jumps +5.0 even though Engram was supposed to be a knowledge lookup.
WALKTHROUGH · PART 1

Why a transformer pays depth for static patterns

A transformer learns everything from scratch every layer. That is a feature for reasoning and a tax for knowledge: the early layers have to reconstruct "the capital of France" as a coherent phrase, then mid-layers have to retrieve Paris, then late layers have to format it for the next token. None of those steps require depth. They require storage.

Mixture-of-Experts (MoE) handled one half of the problem: it made computation conditional, so the network could scale parameters without scaling FLOPs. But MoE is still all computation. The model has no native primitive for looking up a thing it has already memorized, so it routes the lookup through the experts and pays attention + FFN cost on every token.

Why this matters. The headline gain is not knowledge benchmarks. MMLU +3.4 is the expected win. The unexpected win is BBH +5.0 and ARC-Challenge +3.7, because the network now has its early layers free for the parts of the task that actually need thinking.
WALKTHROUGH · PART 2

How O(1) N-gram lookup actually works

The classic problem with N-gram models is the curse of vocabulary. There are ~100k BPE tokens in a typical tokenizer, and v^5 for order-5 N-grams is around 10^25 , which is not a parameter count, it is a heat death of the universe. Engram sidesteps this with three moves.

Move 1: tokenizer compression. A surjective map collapses semantically equivalent tokens. Lowercasing. Unicode folding. Merging 4 into 4. This trims the effective vocabulary by ~23%, which kills most of the combinatorial explosion before it starts.

Move 2: suffix N-grams of multiple orders. For every position t, Engram extracts the suffix 2-gram, 3-gram, 4-gram, and 5-gram ending at t. Short orders catch local collocations; long orders catch idioms and entity names. The retrieved vectors from all orders are concatenated.

Move 3: multi-head hashing. You cannot parameterize every N-gram, so for each order n, you pick K independent hash functions, each of which maps the compressed N-gram deterministically into one of M / K rows of the embedding table. Different heads hash to different rows, which mitigates collisions: the same N-gram appearing in two semantically distinct contexts usually gets retrieved through two different heads and the gate learns to favor the right one.

Why this matters. Three hash heads is a small number. The point is that even with collisions, the gate (next section) can pick which head to lean on, so the system tolerates hash noise the way a transformer tolerates attention noise. You do not need a perfect hash; you need a cheap one that the rest of the model can correct.
WALKTHROUGH · PART 3

The gate is the actual trick

Raw N-gram embeddings are context-blind. The N-gram "Apple" can mean the company, the fruit, or the Big Apple. A static lookup table cannot tell those apart. If you just add the retrieved vector to the residual stream, you get the wrong answer half the time.

Engram fixes this with a learned scalar gate. For each position, the current hidden state from the preceding transformer layer projects into a query vector. The retrieved memory projects into a key vector. The gate is sigmoid(query · key) , clamped near 0 when the context says "ignore this lookup," near 1 when it says "use it."

The gate is also what makes collisions survivable. If hash head 1 and hash head 2 both happen to land on the same row for an unrelated N-gram, the gate will weight whichever head the current token really came from and discard the other. The lookup is the cheap part; the gate is the precise part.

Why this matters. A vanilla N-gram model has the same problem from 1995. What changed is that the gate query is the full hidden state, not a bag-of-words signal. The lookup is stupid. The network around it is not. That is the whole contribution.
WALKTHROUGH · PART 4

The U-shaped allocation curve

You cannot just dump half your inactive parameters into Engram. The paper's "Sparsity Allocation" experiment fixes a total parameter budget, varies the share given to Engram versus MoE, and measures loss. The curve is U-shaped: too little Engram and the model still wastes depth on static knowledge; too much Engram and you have starved the experts that do the actual reasoning work.

The optimum sits around 20-25% of inactive parameters to Engram, with the remaining 75-80% staying in MoE. The intuition is sharp: Engram is dense per-token (every token triggers a lookup), so over-allocating to it inflates every forward pass's compute and storage, while under-allocating leaves the early-layer knowledge tax in place. The sweet spot is exactly where the lookup handles the patterns it should handle and the experts handle the patterns only experts can handle.

Why this matters. Engram is not a replacement for MoE, and MoE is not a replacement for Engram. They are two axes of sparsity that compose. The paper's headline result, Engram-27B beating a strictly iso-parameter, iso-FLOP MoE-27B, comes from allocating the same budget across both axes instead of stacking everything into one.
WALKTHROUGH · PART 5

Why the tables can live in host DRAM

An Engram table with 27B parameters is roughly 54 GB at 16-bit precision. That does not fit on a single accelerator. It does fit in a server's host DRAM.

The trick is that the addressing is fully deterministic. The hash for N-gram g at position t depends only on the compressed tokens, not on any other model state. So the runtime can compute which row to fetch, prefetch the rows for the next few hundred tokens, and overlap the fetch with attention/FFN compute on the accelerator. The paper reports less than 3% throughput penalty when offloading a 100B-parameter Engram table entirely to host memory on 4B and 8B backbone models.

That is the deal that makes the architecture viable. Memory capacity scales with host RAM, not GPU HBM. The model can grow to 100B or 200B of memory without anybody buying a new GPU.

Why this matters. "Memory" as a sparsity axis only works if memory is cheap. The fact that Engram tables can sit in cheap DRAM and be prefetched deterministically is what makes the architecture economically deployable, not just theoretically interesting. RAG has the same memory economics but pays a retrieval round trip; Engram pays a hash.
COMMON CONFUSIONS

What people get wrong on first read

CONFUSION 01

"Engram is just RAG with extra steps."

Wrong. RAG retrieves documents at query time and stuffs them into the context window. Engram retrieves embeddings at every token and adds them to the residual stream through a learned gate, with no context cost and no retrieval round trip.

The right frame: RAG is non-parametric memory at the document level; Engram is parametric memory at the N-gram level. RAG moves bits through context tokens; Engram moves bits through weight deltas.

CONFUSION 02

"Engram replaces MoE."

Wrong. MoE is conditional computation (sparse experts). Engram is conditional memory (sparse N-gram lookup). They are orthogonal axes. The paper's winning recipe keeps MoE for reasoning and adds Engram on top.

The right frame: Drop Engram into a dense model and you under-use experts. Drop it into a pure-MoE model and you get the paper's headline numbers. The U-shape exists because the budget has to be split, not because Engram subsumes it.

CONFUSION 03

"Hash collisions make this useless."

Wrong on the naive read. Hash collisions mean unrelated N-grams sometimes share a row, which sounds fatal for retrieval quality.

The right frame: Multi-head hashing spreads one N-gram across K independent hashes, so the same collision in head 1 is usually clear in head 2 or 3. The gate then weights whichever head's row actually matches the current context. Collisions become noise the network learns to ignore, not a correctness bug.

CONFUSION 04

"If Engram is so good, every new model will use it."

Wrong. Engram is a memory tax, not a free lunch. Adding it inflates every forward pass's storage and bandwidth, even when the gate fires near zero, because you still have to compute the hash and look up the rows.

The right frame: Engram pays off when you have enough static knowledge in the training corpus to fill the table, and when the serving hardware can prefetch deterministically. Small models on small corpora with tight latency budgets will probably skip it. Big pretraining runs with host DRAM to spare will probably adopt it.
