Recursive self-improvement · agent infrastructure

An agent that rewrites its own scaffolding

Harness² treats the prompts, tools, memory and skills around a frozen model as the thing to optimize, and shows you how it does that at test time with no labels and no weight updates.

Harness² keeps the model frozen and rewrites the harness around it, learning which edit helped by comparing how the same task behaved with and without that edit, then writes down the lesson so the next task starts smarter.

The mental model

Two things improve, not one

Most agent improvement stops at the first loop: make this task better. Harness² adds a second loop underneath it that gets better at making the first loop work. The star is on the outer one.

The walkthrough

Six moves

01

The thing being optimized is a folder, not a model

A harness is everything around the weights: the system prompt, guardrails, memory, skills, tool guidance, scripts, subagents, and plugins. In Harness² each of those eight is a file mounted into the agent runtime. The editors are told to treat them as editable source.

That framing is why no gradients appear anywhere in the paper. Nothing is trained. The unit of change is a diff on a markdown file, and the unit of learning is an observation about what the agent did afterward.

Why this matters

You already own a harness. Whatever prompts, CLAUDE.md, skill files and scripts your agent runs on are part of this scheme. The claim is that this layer is where the next large gains are, and that it is editable by an agent at runtime without touching weights.

02

The problem: nobody knows if the answer was right

Open-world tasks arrive without ground truth. There is no test to pass and no reference answer, so the usual gradient-free self-improvement loop has nothing to climb. Prior work papers over this with proxy signals, assumed answers, or pairwise output judging.

Harness² makes the honest move: it stops trying to score correctness. Instead it runs the task twice, once with the current harness and once with an edited one, and reads the difference in behavior. The question shifts from "was this right?" to "did this edit change what the agent did?".

Why this matters

This is the load-bearing idea, and it transfers to anything you build. If you cannot score an output, you can still diff two behaviors under controlled conditions. That is a weaker signal than correctness, and the paper is careful to say so, but it is a signal you can act on at test time.

03

Two editors, deliberately pointed at different things

Each step proposes two candidates from the same reference. The invariant editor hunts for agentic deficiencies that will show up again next week: skipping tool calls, losing context, never verifying its own work, delegating badly. The domain-specific editor writes down the facts of the current situation, which are useful today and worthless tomorrow.

That split is doing real work. The ablation says replacing both editors with generic ones costs 2.9 points on WorkBuddy and 3.7 on JobBench, even though the same number of candidates still gets drafted and probed. Naming the scope is what makes the contrast readable.

Why this matters

If you build anything that learns from agent runs, keep these two buckets separate. Merging durable behavioral rules with task-specific facts is how a memory layer turns into a pile of stale trivia that slowly degrades every later run.

04

Compose makes the proposals into parts, not finalists

The obvious design would pick the better of the two candidates and ship it. Harness² does not. The composer reads every candidate, its diff against the current harness, and the observed behavior, then merges the edits that the evidence supports, revises the ones that conflict, and can also decide to change nothing.

Every decision has to point at a concrete observation. Dropping composition entirely, and just returning whichever candidate the evidence favors, still beats the base harness. It just leaves about 1.6 points on the table on WorkBuddy.

Why this matters

Candidate selection throws away information. Composition keeps the part of an idea that the evidence supports even when the candidate as a whole lost. That is also why the cost is what it is: you are paying for multiple executions and several editor sessions per task, and the paper is upfront that raising the budget raises inference cost.

05

The second loop learns how to improve

Here is the part I keep coming back to. Improving the harness for one task produces a trail: which deficiency was diagnosed, which edits were tried, what each one actually did to the agent's behavior. Most systems throw that trail away after the deliverable ships.

Harness² reads the whole improvement record and writes a library entry per task: the adopted harness plus an EXPERIENCE.md holding the shape of the situation, the transferable lesson, and the execution evidence behind it. The next task starts from the same base harness, but the proposer can now reach into that library. Two details make this honest rather than a scrapbook. A lesson is kept only when execution evidence supports it, and when the evidence is too thin the system writes nothing rather than guessing.

Why this matters

Removing the library costs 3.1 points on WorkBuddy and 1.8 on JobBench, and the paper also shows a library built on JobBench transferring to WorkBuddy. A lesson that names a pattern rather than this task's facts is a lesson that can fire on something you have never seen.

06

What the numbers actually say

Gemini 3.5 Flash under OpenCode, WorkBuddy-Bench, means across three domains. The base harness averages 72.4. One Harness² step takes it to 77.5. Parallel recursion at k=5 takes it to 80.8. The baselines they compare against are real systems: ReasoningBank, Harness Scaling, and Meta-Harness, which is the strongest of them at 76.4.

The same model, the same starting harness, no weight changes. The gains hold across four executor-harness configurations including settings where the same model plays both executor and editor. And they are not free: the compute-perf frontier favors Harness², but every point above the baseline was bought with more executions.

Why this matters

Nothing here required a smarter model. The base model already knew it should call tools; the harness had not told it so clearly enough, and the harness was the thing that got rewritten. Read the ablation table and the pattern holds: removing skills costs 4.3 points, removing the prompt group costs 3.7, and every ablated harness still beats the base.

Common confusions

Four things worth getting right

01

"It's just the agent rewriting its own prompt until it feels good."

That framing makes it sound like a loop of vibes with no evaluation inside.

The actual loop has a control. Every candidate runs under matched conditions against a reference execution, and composition only keeps edits tied to an observed behavior change. The paper's reflector prompt even tells the system to prefer the verdict "confounded" over an invented attribution, and to write nothing when the evidence is thin.

02

"The improvement loop uses self-reward or an LLM judge to pick the winner."

This is the standard fallback when no ground truth exists, and Harness² is explicitly not that.

Selection is blind to provenance, by design. At k greater than 1 a selector compares anonymized deliverables, so it can say which output reads best but not which edit produced it. The authors note the star on the adopted harness means adoption, not verified optimality. Evidence comes from execution contrast; the judge only picks a deliverable.

03

"A harness that worked on this task carries forward to the next one."

It sounds like the harness accumulates, which is exactly the noisy-recursive-improvement trap.

Every task restarts from the same base harness H0. What carries forward is the library of adopted harnesses plus their lessons, and components get reused or adapted deliberately through Propose rather than inherited wholesale. Tailoring that sticks around is how accumulated edits start fighting each other.

04

"Better scores mean it got better at reasoning."

It is tempting to read the benchmark deltas as a capability change.

The weights never move. The gains come from harness edits, and the paper shows a wide gap between strong and weak settings at zero training cost. It also shows how it can go wrong: the selector picked a 55 over a 95 on one case, and a wrong premise baked into a candidate spread across probes and cost 11 points on another. This is scaffolding quality, not model quality.
