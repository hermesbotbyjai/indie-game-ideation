When the model names its own context window

Declarative Attention turns attention selection from something the serving engine guesses into something the model writes down. The engine reads the plan straight off the output tokens and skips the KV cache blocks that plan says are irrelevant.

ProblemEvery decoding step reads the whole KV cache, even when 99% of it is noise.
MoveThe model emits <global>, <focus>, or <local> tags mid-reasoning.
MechanismA tag state machine turns those tags into a per-step attention mask.
Result20-46% fewer attended tokens for 1.4-2.1 points of accuracy.
The model in one sentence
One sentence, and that is the whole idea

The model writes its attention plan into its own output as <global>, <focus chunk="7">, or <local> tags, and the inference engine parses those tags like tool calls to build a KV cache mask, so the chunks the model just declared irrelevant are never read from memory.

Mental model

The plan and the reads are the same tokens

Sparse attention has always been an inference problem: some separate scorer looks at the activations and guesses which keys matter. Declarative Attention inverts that. The model already knows, somewhere in its forward pass, which part of the context it needs next. DA gives it a syntax for saying so out loud, and the serving runtime treats that text as the schedule.

Walkthrough

Five pieces, in the order the runtime sees them

Step 01

Why reading the whole cache is the expensive part

A transformer decodes one token at a time, and at every step the global-attention layers need a key and a value for every token that came before. That means the decode loop streams the entire KV cache out of HBM on every single token it emits. For a 1M-token conversation, every token you generate costs a full scan of a gigabyte-scale cache.

Here is the thing that makes this painful. The attention weights themselves are already concentrated. The model is looking at a handful of tokens and ignoring the rest. The waste is not in the math, it is in the memory traffic.

The paper's Appendix C puts a number on it: attention dominates decode time by roughly two orders of magnitude in the long-context regime, around 145x at their reference operating point.

Why this matters

If you are running long-context inference at scale, your bill is dominated by memory bandwidth, not FLOPs. A technique that skips reads wins on latency and on cost per token at the same time, which is rare.

Step 02

Why every previous sparse attention method still pays O(N)

The obvious fix is to score the context and only fetch the winners. That is what a lot of production systems do. The problem is that the scoring itself is a linear pass over the context, so you are paying O(N) to avoid paying O(N).

The paper calls this the extrinsic approach, and it has a good reason to exist: the scorer is a separate model that never has to change the main model's behavior. It is bolted on. It is also why the 2026 frontier models went a different direction: DeepSeek-V4, GLM-5, and Qwen3.8-Flash-Next all use indexer-based sparse attention where a cheap index picks a top-k set, and the index scan is still O(N) per step.

Declarative Attention asks a different question. If the model already knows what it needs, why not just read that knowledge off the output stream?

Why this matters

This is where DA is complementary rather than competing. The authors are explicit that global mode still costs O(N) attention, and that this cost is orthogonal to the protocol, so DA can be layered on top of an indexer-based sparse model.

Step 03

The three modes, and what each one is for

DA partitions generation into three modes. The model picks freely, as often as it wants, and the protocol does not restrict how or when.

<global> sees everything. Use it to navigate, to find where the answer lives. <focus chunk="7"> sees one or more named chunks and nothing else. Use it to read closely. <local> sees no context at all, just the scaffold and the model's own output so far. Use it to synthesize what it already found.

The context is pre-segmented into chunks of roughly 2048 tokens, cut at paragraph breaks where possible so the boundaries land on semantic seams. Each chunk gets an id, and the model refers to chunks by id.

Why this matters

The mode split is what makes this more than a cache eviction trick. Focus mode is a deliberate re-read of one region. Local mode is deliberate forgetting of everything else, which is how you keep the model's reasoning honest about what it actually retrieved rather than what it half-remembers from a 1M-token blur.

Step 04

The state machine that turns text into a mask

The runtime parses the tag stream as it decodes. Nothing about this needs a separate model or a separate scoring pass. The tags arrive interleaved with the reasoning, so the plan and the reads are the same tokens.

Three regions stay attended in every mode: the scaffold (system instruction, question, DA instruction), the model's own response so far, and a fixed 16-token attention sink at the head of the prompt. The sink trick is why the system instruction is padded with content-free text, so the sink never eats real context.

Nesting is supported. A focus region opened inside a local region unwinds correctly when the closing tag arrives, which is what lets you write a small state machine instead of a flag.

Why this matters

Reversibility is the quietly important part. Compaction, the technique agentic systems use to shrink history, is destructive: the summary replaces the original tokens and their KV cache is discarded, so bringing anything back means re-prefilling from text. DA never edits the sequence, so a chunk that sits masked can be restored the instant a later tag asks for it.

Step 05

What it actually costs, and what it actually buys

The headline numbers: across 15 long-context tasks, zero-shot, on off-the-shelf models, DA cut total attended tokens per response by 45.8% for Gemma-4-31B and 19.6% for Qwen-3.6-27B, with accuracy drops of 1.40 and 2.10 percentage points. The gap narrows as the model gets bigger.

There is a catch that the paper is upfront about. The protocol makes the model write out its plan, so DA runs about 15-35% more decoding steps than vanilla. The per-step saving has to outrun that overhead, and on tasks where the model emits one unit of output per segment, attended tokens accumulate end-to-end anyway. That is a decode-length problem, not an accuracy one, and the authors suggest routing verbose output through focus mode to bound it.

Scoring was done with an LLM judge: a strict rubric generated by Gemini-3-Flash, applied by a thinking-enabled Qwen-3.5-4B that correlates with Gemini-3.1-Pro at r = 0.99.

Why this matters

Nothing here is trained. No fine-tuning, no RL, no parameter updates. It is a prompt, a delivery format, and a state machine. You can try it on your own serving stack this afternoon, which is also why it is worth understanding the mechanism rather than just the headline percentage.

Common confusions

Four things people get wrong

Confusion 01

"This is just attention sparsity with extra steps."

Wrong framing. Indexer-based sparse attention predicts which keys matter from activations, and still scans. DA does not predict anything. The model states the answer in text and the runtime reads it off. The mechanism is different, and the O(N) index scan disappears with it.

Confusion 02

"The model is choosing to ignore context, so it might miss things."

Not how it works. The scaffold, the question, and the model's own output stay attended in every mode. Only the addressable context chunks are masked, and masking is reversible because the KV cache is never evicted. A chunk masked in one step can be unmasked in the next.

Confusion 03

"Fewer attended tokens means proportionally faster."

Not necessarily. The protocol makes the model write its plan out loud, so DA runs 15-35% more decode steps than vanilla. The per-step saving has to outrun that. On verbose-output tasks the authors concede that attended tokens accumulate end-to-end anyway.

Confusion 04

"This needs a trained model or a custom architecture."

No training required. DA runs zero-shot on off-the-shelf Gemma-4-31B and Qwen-3.6-27B. There is no parameter update anywhere. The reference implementation is a state machine plus a vLLM integration, and the community already has standalone PyTorch and llama.cpp versions.

Where to go next

Three specific things worth reading

  • The paper, with the appendix that has the real numbers

    The v1 HTML version is the one to read: it carries the attention mask figure, the KV-bytes-per-token table comparing MiniMax-M3, GLM-5.2, DeepSeek-V4 and Qwen, and the vLLM integration details. Appendix C is where the roofline derivation lives.

    arxiv.org/abs/2609.02737

  • The reference implementation on vLLM

    The official repo ships dattn: the tag state machine, prompt layouts, compacted attention metadata on vLLM, plus eval and paired-timing tools. If you want to see how a tag becomes a paged-attention block mask, this is where it happens.

    github.com/itsnamgyu/declarative-attention

  • The llama.cpp fork, for the server-side view

    A community fork implements DA on stock llama-server, which needs server changes because the upstream has no way to touch KV ranges mid-generation. It also shows the roofline claim translated into a serving deployment.

    discussed on r/LocalLLaMA · focus-llama
