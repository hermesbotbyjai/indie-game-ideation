The model in one sentence

One sentence

An LLM can't prove your code is correct, but it can prove your code matches a spec, which collapses the amount of software anyone has to trust by hand into a fixed handful of components.

Mental model

The bug surface doesn't grow. The trusted base does not either.

Picture two stacks. The left one is what you're running. The right one is what someone has to be correct about. Verification only works if the right stack stays small while the left one grows.

The verification work moves code above the trust line. The trust line itself doesn't move, so verifying the thousandth dependency costs the same in trust as verifying the first.

Why this matters

Every guarantee in this field has always been gated on human effort, and human effort is the one input that doesn't scale with your GPU budget. If the model absorbs proof-writing, the economics change from "we cannot afford to verify the hundredth library" to "we can verify everything, once."

Walkthrough

How a fuzz test becomes a theorem

1. You already wrote the spec. You just didn't call it one.

Here's the move that makes this work at all, and it isn't about model quality. You need to state what "correct" means before anything can be proved about it, and for most software that's genuinely hard. What does it mean for a browser to be correct? Nobody has that spec.

Anthropic sidestepped it by noticing that the spec already existed. Every project in Google's OSS-Fuzz has an entry point a developer wrote, and an engineer already decided that any input causing a crash there is a bug worth caring about. Encoding "this test never crashes" is a complete, unambiguous spec, and it was sitting in the repo the whole time.

Sampling finds bugs it lands on. Proving is the quantifier over everything, which is why one proof retires an entire fuzzing campaign.

Why this matters

This is the reusable trick for your own codebase: you almost certainly have crash-observing harnesses sitting in CI right now. Each one is a spec statement you could be proving instead of re-fuzzing forever. That is the cheapest first move into formal verification, and it needs no new tooling to identify.

2. Two theorems are not enough. You need three.

This is the part the headline skips, and it's the part that would bite you in review. OSS-Fuzz runs binaries with AddressSanitizer compiled in. Users run the normal binary. ASan changes the program's behaviour. Proving the instrumented binary is crash-free tells you almost nothing about what ships.

So the guarantee takes three separate theorems. First: the ASan binary never crashes. Second: the ASan binary and the normal binary are observationally equivalent, meaning same stdin, same stdout and stderr, same exit code or signal, same final filesystem state. Third, and this is the one people forget: the normal binary doesn't crash either. Without it you have a hole where the normal binary crashes in a branch where the instrumented one silently loops, and equivalence never notices.

Three theorems, each a real cost, each covering a gap the others leave. Assuming away the third is how "we proved it" quietly stops meaning anything.

3. The proof is thirty times the code, and that's the expected shape.

The numbers here will look absurd until you understand where the lines go. Claude wrote around a billion lines of Rocq attempting to prove a few hundred entry points; about 180 million survived the proof checker.[2] A finished proof runs roughly 600,000 lines across about 1,400 files.

cJSON's 391-line parser got a 630,000-line proof. In cJSON's proof, only about one-tenth of the lines concern cJSON at all. The rest is C runtime startup, the allocator, printf, ASan's own runtime and the fuzz driver, all re-proven from scratch because none of it is shared. Proof size barely tracks the library's size, and that is the honest headline: the economics work because the per-library overhead is enormous, not because the overhead is small.

Most of the proof is shared infrastructure that gets re-proven per library. Sharing it across proofs is the single biggest cost lever available.

Why this matters

It also tells you where to push if you ever run this yourself. Proof reuse is the lever. Anthropic measured it: agents allowed to copy each other's finished proofs needed 17% fewer tokens, and some that failed solo succeeded once they could see a neighbour's work.[1] Most of a proof is code every program contains, so the overlap is enormous by construction.

4. The bugs fuzzing structurally cannot find.

Fuzzers mutate inputs and cap out around 1 MB by default. They find the bugs reachable from the inputs they happened to generate. Attempting a proof surfaces a different set entirely.[1]

Claude found a counter underflow leading to an out-of-bounds write that only triggered on inputs near 20 MB with one rare layout. An out-of-bounds read in an image decoder needing a 64 MB input and over 2 GB of memory. An out-of-bounds read requiring a particular call sequence across two handles to the same file. And a logic bug that never crashes at all, where a file-loading restriction was not consistently enforced.

Fuzzing samples a dense region. Proofs cover the whole space, including the corner nothing was going to stumble into.

5. Where the agent proofs stop scaling.

This is the most useful section in the appendix, and almost nobody read it.[2] Claude's proofs are correct, since the checker validates them. But they're written in a style that will not scale.

The pattern: the agent spells out every register's contents, every integer conversion, every individual address being distinct from every other, every branch in a function. All of it is genuinely required to reason about execution. A human proof engineer would have stopped at step one and abstracted: a calling convention, a set of disjoint pointers, an allocator model, one lemma covering every branch. Claude sometimes does introduce these. When it does, proof size drops, but only modestly, and the verbosity persists.

There's a second thing worth noticing. Asked to prove two binaries equivalent, the agents usually didn't prove equivalence directly. They first synthesized a short spec describing what the program can output, then proved both binaries conform to it. Median spec: about 110 lines, against a median program of 86 KB.[2] That is a genuinely interesting capability and nobody asked for it.

Both columns prove the same theorem. Only one of them survives contact with a program twenty times the size.

Why this matters

Prior agent verification work, cited in the appendix, hit exactly this wall and scaling required better modular abstractions.[2] The open research question is whether agents can be taught to invent good abstractions unprompted, or whether this needs expert proof engineers in the loop. That question decides whether the cost curve keeps falling. Right now it isn't settled, and pretending otherwise in a design doc would be a mistake.

6. The cost curve, and the one assumption that quietly limits all of it.

Two things are pushing cost down. Newer models are cheaper on the same work: Opus 5.5 proved half of 36 benchmark tasks using about 40% fewer tokens than Opus 5.[1] And reuse, covered above, gives another 17%. Dependencies also follow a power law, so verifying a small set of shared libraries makes a large amount of downstream software provable for free.

The limitation is worth sitting with. These proofs assume single-threaded static binaries, a fixed memory budget, RISC-V, and Linux. Most people deploy on x86 or ARM, dynamically linked against glibc. ASan doesn't catch every memory safety bug, not every entry point was verified, and verifying all entry points still doesn't cover dead code or callers who misuse your API. A proof checker can tell you the code matches the spec. It cannot tell you the spec matches reality.

Being honest about this edge is what separates a real security argument from a marketing one. The gap is named, bounded, and shrinking.

Common confusions

Four things people get wrong about this

01

"Formally verified" means bug-free

The proof shows the binary satisfies the spec. The spec was written by someone, and nothing checks whether it describes reality.

When bugs show up in verified code, it's because the spec or the assumed machine semantics diverges from the real world. That's a much more useful situation than "there are bugs somewhere", because you know exactly where to look. The three things a human must trust are the Rocq checker, the RISC-V semantics, and the Linux process semantics.[1]

02

The proofs need expert review

180 million lines of Rocq can't possibly be human-checked, so the output is unauditable and therefore worthless.

Nobody reviews the proofs. The checker does, and it rejects anything invalid. Review effort goes to the spec statement and the machine semantics instead. That's the entire point of the trusted-base argument: 180 million machine-checked lines cost you the same human attention as three hand-reviewed components.

03

This replaces fuzzing

Proofs strictly dominate, so fuzzing is now obsolete and teams should move off it.

It's narrower and more expensive per target. ASan doesn't catch every memory safety bug, not every entry point got verified, and verifying all entry points still misses dead code and callers who misuse your API. Fuzzing is a sampler and proofs are exhaustive over a scope, but the sampler is currently far cheaper and covers the parts the proofs don't reach.[1]

04

The model is doing formal mathematics

Claude understands program semantics and reasons about correctness like a theorem prover.

It generates candidate proof steps and iterates against the checker. Every accepted proof is mechanically validated by Rocq, not by Claude. The model's job is search, not judgment, and every claim of soundness comes from the checker. That's also why the format, the semantics and the checker are the only three things anyone needs to trust.
