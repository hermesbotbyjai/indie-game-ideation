Hierarchical Memory Trees for Agents

A long-term agent memory that only stores the current predictor is provably incomplete. The real continued-learning state is a tree of plain files organized by time and topic, walked down by the agent the same way it walks your codebase.

The Model in One Sentence

An agent's long-term memory should be a time-organized tree of plain files, not a vector store and not a frozen summary, because storing only the current predictor is provably lossy and the agent must walk the tree to find the few hundred tokens a task actually needs.

Theory: Prediction Is Not a Sufficient Memory State (Alvarez, 2026). Practice: IHMT, shipped this week.

Walkthrough

Five ideas that earn their place.

Each section is one claim, one diagram, one reason it matters. Read in order if this is your first pass; jump in from "Common confusions" if you want the receipts.

1. Storing the current predictor is provably insufficient.

A learning system that fits a model y = f(x) might think it has learned when, in fact, it has collapsed information that future updates still need. The 2026 paper Prediction Is Not a Sufficient Memory State proves this in the cleanest possible setting: for any agent whose state can be summarised by its current predictor, there exist two histories that produce identical predictions forever, yet respond to the same next input in different ways.

The math is precise. For degree-D polynomial losses with d features, the recurrent state needs exactly binom(d+D, D) - 1 coordinates, and even when you fix the predictor, r - d of those are invisible on the prediction alone.[1]

Why this matters If your memory is "the model's answer," you have lost the past. If your memory is a tree of past observations, the agent can recover the relationship it needs to update. The architecture decision and the storage decision are the same decision.
Fig 2 · Two histories, one predictor

2. The tree is organized by time, not topic.

This is the part that feels counterintuitive. Most "memory" systems group by topic (projects/, people/). Hierarchical memory trees group by recency horizon: recent/ for active context, stable/ for things that should never change, archive/ for everything that did.

The reason is operational. Recency tells you what to read first and what to trust. Topic doesn't. If the agent is debugging a Postgres migration, it needs the most recent shard of context; "projects" is the wrong axis.[2]

Fig 3 · Recency first, topic nested inside
Why this matters When a memory is grouped by recency, "is this still right?" is one folder glance. When it is grouped by topic, you have to remember the topic or search for it. Topic is what the model thinks the world looks like. Recency is what time did to that model.

3. Search walks the tree, it does not dump it.

The cost claim is the one that gets attention: 200 to 900 tokens per query whether the memory is 50 entries or 50,000.[2] But the more important property is qualitative. A walk respects hierarchy. A dump flattens it.

When the agent asks "what's our staging DB?", a good hierarchical search goes root → STABLE/identity.md → the line. A flat retrieval returns whatever happens to have the highest cosine similarity, which often is a paragraph of an unrelated decision that mentioned staging once.

Why this matters The tree is not a clever way to write a vector store. The tree is the index. Cosine similarity is the fallback when the index fails.
Fig 4 · Walk vs. flatten

4. Outdated is a folder, not a flag.

Most memory systems have one rule for "this used to be true." They append a stamp like [DEPRECATED 2026-09-01] to the current fact. That sounds fine and it isn't. If you only edit the front, every old decision with the wrong cutoff time will quietly misdirect future searches.[2]

The hierarchical answer is structural: archive/ is a first-class folder, every file there is still readable, and the search returns the current fact first. When the user changes cities, the old city stays. When stacking changes, the old stack stays. The tree gets larger and the answer stays correct.

Why this matters A memory that forgets things is broken in the obvious way. A memory that pretends to remember the new and the old as one blob is broken in the way that ships to customers.
Fig 5 · Outdated lives in its own branch

5. The cost model is in tokens, not files.

The agent retrieves what a query needs. With IHMT, that's reported as 200 to 900 tokens per call on read, whether the tree has 50 or 50,000 entries.[2] The reason isn't clever chunking. It's that hierarchy gives you index slices you can ignore.

Put another way: a flat RAG indexes by similarity. A tree indexes by knowing what time and topic a thing is. The first is a content index. The second is a memory. Add to that the honest limits: search cost is roughly linear in number of files you walk, and you still pay a model step at every node.

Why this matters Cost in long-term agent memory is not about the size of what you store. It is about the size of what you read. The tree buys you a much smaller read for a slightly larger store.

Common Confusions

Four ways this quietly lies to itself.

If you remember only the pictures, remember these.

1

CONFUSION: "the model's summary is the memory"

A summary is what the model believed the last time it produced one. The Alvarez proof shows this is lossy in a specific way: two histories with identical predictions diverge on the next observation. Store observations, not summaries.[1]

2

CONFUSION: "a vector store is enough"

Vector search finds what looks like what you asked. It does not find what is still true. When you live in Valencia but your stack is described by old cosine neighborhoods, "Madrid" still scores above zero. Hierarchy is the indexing layer vectors don't replace.

3

CONFUSION: "more memory is always better"

Every folder walked is one more model step. A tree with 50,000 files is a tree with 50,000 chances to misroute. The point of hierarchy is to keep the working set small by knowing what to ignore, which is the opposite of stuffing.

4

CONFUSION: "outdated memories should be deleted"

The agent will be asked "what was it before?" and the wrong answer looks worse than the right one with a date. Old facts are not noise; they are the audit log. Move them, don't drop them.[2]
